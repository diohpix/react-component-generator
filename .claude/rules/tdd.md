# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.**
> 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다. 규칙의 문구를 지키는 것이 곧 규칙의 취지를 지키는 것이다.

## 0. 우선순위 (프로젝트별 규칙 우선)

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 관련 규칙이 있으면 **그 규칙이 이 파일보다 우선한다.**
- 이 파일은 프로젝트에 별도 규칙이 없을 때 적용하는 **기본값(fallback)**이다.
- 충돌하는 항목만 프로젝트 규칙을 따르고, 나머지는 이 파일을 그대로 적용한다.

## 1. 적용 기준

### TDD를 반드시 적용하는 대상

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 변환, 에러 매핑)
- **유틸리티 / 순수 함수**
- **버그 수정** — 버그를 재현하는 실패 테스트를 먼저 작성한 뒤 고친다

### TDD가 불필요한 대상

- **타입 정의** (`type`, `interface`)
- **설정 파일** (빌드, 린트, 환경 설정 등)
- **순수 UI** (로직 없는 마크업/스타일)
- **SQL** (스키마, 마이그레이션, 쿼리 스크립트)

경계가 모호하면(UI 안에 분기 로직이 섞인 경우 등) 로직을 순수 함수로 분리해 그 부분에 TDD를 적용한다.

## 2. RED - GREEN - REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 검증하지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류, 잘못된 설정으로 인한 실패는 RED가 아니다. 먼저 고친 뒤 다시 실패를 확인한다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트나 전제를 다시 점검한다.

### GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 분기, 옵션, 일반화, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과하는지 전체 실행으로 확인한다.** 새 테스트만 돌리고 끝내지 않는다.
- 통과를 위해 테스트를 약하게 고치지 않는다. 테스트가 틀렸다면 RED로 돌아가 테스트부터 바로잡는다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출처럼 **동작을 바꾸지 않는 정리만** 한다.
- **모든 테스트가 green인 상태를 유지한다.** 변경 후 매번 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 시작한다.

### 반복

- 다음 동작이 있으면 **RED로 돌아간다.** 한 사이클이 끝나기 전에 다음 동작의 코드를 미리 쓰지 않는다.

## 3. 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 클립보드 보관, 기억해 두고 다시 타이핑하는 것 모두 포함한다. 코드를 보면서 테스트를 쓰면 구현에 맞춘 테스트가 되어 검증력이 사라진다.
- 삭제 후에는 테스트가 요구하는 만큼만 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트가 필요 없다" | 단순한 코드는 테스트도 단순해서 비용이 거의 들지 않는다. 단순하다는 판단이 틀려서 생기는 버그가 가장 오래 숨어 있다. 단순하면 더더욱 지금 쓴다. |
| "테스트는 나중에 추가하겠다" | 나중에 쓰는 테스트는 구현을 그대로 베끼는 테스트가 되고, 실제로는 쓰이지 않는 경우가 대부분이다. 테스트가 먼저 실패하는 것을 못 봤다면 그 테스트가 무엇을 검증하는지 알 수 없다. |
| "시간이 없다" | 실패 테스트 없이 짠 코드의 디버깅과 회귀 수정이 더 많은 시간을 쓴다. 급할수록 사이클은 짧게, 하지만 생략하지 않는다. |
| "삭제하면 낭비다" | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. TDD로 다시 쓰면 대개 더 짧고 단순해진다. |
| "프로토타입이라서 괜찮다" | 프로토타입은 거의 항상 그대로 제품이 된다. 버릴 코드라면 테스트도 쉽게 버릴 수 있으니 비용 차이가 없다. 적용 대상이면 프로토타입도 예외가 아니다. |

## 5. 완료 전 점검

- [ ] 구현보다 테스트를 먼저 작성했는가
- [ ] 각 테스트가 "기능 미구현"으로 실패하는 것을 직접 확인했는가
- [ ] 신규 + 기존 테스트가 전부 green인가
- [ ] 리팩터링 단계에서 새 동작을 추가하지 않았는가
- [ ] 버그 수정이라면 재현 테스트가 수정 전에 실패했는가
