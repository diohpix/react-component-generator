# Commit

변경사항을 읽고 의미 있는 단위로 나눠, 이 저장소의 컨벤션에 맞는 한국어 커밋 메시지로 기록한다. 사용자가 커밋을 요청한 것 자체를 승인으로 간주하므로, 별도의 확인 질문 없이 바로 커밋하고 결과를 보고한다.

## 절차

### 1. 변경사항 분석

아래를 병렬로 실행해 현재 상태를 파악한다.

- `git status --short` — 수정/신규/삭제 파일 전체 (untracked 포함)
- `git diff` 와 `git diff --staged` — 실제 변경 내용
- `git log --oneline -10` — 최근 메시지 스타일 확인 (스코프 사용 여부, 어투)

신규(untracked) 파일은 diff에 나오지 않으므로 필요하면 내용을 직접 읽는다. 변경이 없으면 "커밋할 변경사항이 없다"고 알리고 끝낸다.

민감 파일(`.env`, 키·토큰·인증서, 자격증명 파일)이나 빌드 산출물(`node_modules`, `dist` 등)이 변경 목록에 있으면 커밋 대상에서 빼고 사용자에게 알린다. 한 번 커밋되면 히스토리에서 지우기 어렵기 때문이다.

### 2. 논리적 단위로 분류

"하나의 커밋 = 하나의 이유"가 되도록 나눈다. 리뷰어와 `git revert`·`bisect`가 쉬워지기 때문이다.

- 기능 추가, 버그 수정, 리팩터링, 설정/의존성 변경은 서로 다른 단위다.
- 같은 목적에 속한 코드·테스트·타입 변경은 함께 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p` 대신 hunk 단위로 나눌 수 있는지 먼저 판단한다. 비대화형 환경에서 어렵다면 하나로 묶고 그 이유를 사용자에게 말한다.
- 변경이 작고 단일 목적이면 억지로 쪼개지 않고 커밋 1개로 한다.

### 3. 커밋 메시지 작성

형식:

```
<type>(<scope>): <한국어 요약>

<선택: 본문 — 무엇을 왜 바꿨는지>
```

- **type**: `feat`(기능 추가), `fix`(버그 수정), `refactor`(동작 변경 없는 구조 개선), `chore`(설정·빌드·의존성·스킬 등 잡무), 필요 시 `docs`, `test`, `style`, `perf`
- **scope**: 선택. 영향 범위가 뚜렷할 때만 쓴다 (예: `chore(skills)`). 3단계에서 확인한 최근 로그의 관례를 따른다.
- **요약**: 한국어, 한 줄, 가급적 50자 안팎, 마침표 없음. "무엇을 했는가"보다 "무엇이 달라지는가"가 드러나게 쓴다.
- **본문**: 요약만으로 이유가 전달되지 않을 때만 쓴다. 변경 목록을 나열하기보다 *왜*를 적는다.

예시:

```
feat(generator): Google 모델 실패 시 자동 폴백 추가
fix: 컴포넌트 이름이 숫자로 시작할 때 생성이 실패하는 문제 수정
refactor(api): 프롬프트 조립 로직을 별도 함수로 분리
chore: Claude Code 워크트리 설정 추가
```

현재 세션에 커밋 attribution(Co-Authored-By 등) 지침이 주어져 있으면 그 지침대로 메시지 끝에 덧붙인다.

### 4. 커밋 실행

승인을 기다리지 않고 단위마다 바로 커밋한다.

- 단위마다 **해당 파일만 명시적으로 `git add <파일들>`** 한 뒤 `git commit`한다. `git add -A`/`git add .`는 의도하지 않은 파일(민감 파일 포함)을 쓸어 담을 수 있어 쓰지 않는다. 이미 staged된 다른 파일이 있으면 섞이지 않게 먼저 정리한다.
- 메시지는 HEREDOC으로 전달해 줄바꿈과 따옴표가 깨지지 않게 한다.
- 모두 끝나면 `git log --oneline -n <커밋 수>`로 결과를 보여주고, 어떤 단위로 나눴는지 짧게 설명한다.

## 하지 말아야 할 것

- `git push`, `--amend`, `--no-verify`, `reset --hard` 등은 사용자가 따로 요청하지 않는 한 하지 않는다. 이 스킬의 범위는 로컬 커밋까지다.
- pre-commit hook이 실패하면 우회하지 말고 원인을 보고한다. 수정 후에는 amend가 아니라 새 커밋을 만든다(실패한 커밋은 생성되지 않았으므로 amend하면 이전 커밋을 덮어쓴다).
