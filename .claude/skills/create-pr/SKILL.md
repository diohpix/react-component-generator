# Create PR

현재 브랜치의 변경사항을 분석해 PR 본문을 쓰고 `gh`로 Pull Request를 만든다.

이 스킬은 `context: fork`로 별도 컨텍스트에서 실행되므로 사용자에게 중간 질문을 할 수 없다. 판단이 필요한 지점은 아래 기본값으로 결정하고, 결정 내용과 결과(PR URL)를 마지막 보고에 모두 담는다. 허용 도구는 Read, Glob, Grep, Bash뿐이라 파일 수정은 하지 않는다. PR 본문은 Bash의 `gh pr create`로 직접 전달한다.

## 절차

### 1. 사전 점검

아래를 병렬로 실행한다.

- `git branch --show-current` — 현재 브랜치
- `git status --short` — 미커밋 변경 여부
- `git remote -v` 와 `git rev-parse --abbrev-ref @{upstream}` — 어느 remote로 push할지. remote가 여러 개일 수 있으므로 upstream이 가리키는 쪽을 우선한다.
- `gh repo view --json defaultBranchRef,nameWithOwner` — base 브랜치(기본 브랜치)와 대상 저장소
- `gh pr list --head <현재 브랜치> --state open` — 이미 열린 PR이 있는지

다음 경우에는 PR을 만들지 않고 이유를 보고하며 끝낸다. 잘못된 PR은 리뷰어 알림을 발생시키고 정리 비용이 들기 때문이다.

- 현재 브랜치가 기본 브랜치(`main`/`master`)다 → "작업 브랜치를 만든 뒤 다시 요청해 달라"고 안내한다.
- 기본 브랜치 대비 커밋이 0개다.
- 같은 브랜치의 열린 PR이 이미 있다 → 그 PR의 URL을 알려 준다.

미커밋 변경이 있으면 PR에는 커밋된 내용만 들어간다는 점을 보고에 적는다(커밋은 하지 않는다).

### 2. 변경사항 분석

base는 1단계에서 얻은 기본 브랜치이며, 아래 `<base>`는 `origin/<기본 브랜치>`처럼 실제 remote 참조로 바꿔 쓴다.

- `git log <base>..HEAD --format='%h %s%n%b'` — PR에 포함될 커밋들
- `git diff <base>...HEAD --stat` — 변경 파일 규모
- `git diff <base>...HEAD` — 실제 변경 내용. 크면 핵심 파일 위주로 읽는다.

커밋 메시지는 "무엇을 했나"를, diff는 "실제로 무엇이 바뀌었나"를 알려 준다. 둘이 어긋나면 diff를 따른다. 본문은 커밋 목록을 옮겨 적는 것이 아니라 리뷰어가 알아야 할 *왜*와 *영향 범위*를 정리하는 것이다.

관련 이슈 번호는 브랜치 이름이나 커밋 메시지(`#123`)에서 찾아 보이는 경우에만 연결한다. 추측하지 않는다.

### 3. 언어 판단과 템플릿 선택

프로젝트 언어를 아래 순서로 판단한다. 앞의 근거가 뚜렷하면 거기서 멈춘다.

1. `CLAUDE.md`/`AGENTS.md`에 응답·문서 언어 지침이 있으면 그것을 따른다.
2. 최근 커밋 메시지(`git log -10 --format=%s`)의 언어
3. `README.md`의 언어

한국어(한글 위주)면 `references/pr-temp.md`의 **KR** 섹션, 그 외에는 **EN** 섹션을 쓴다. 판단이 갈리면 최근 커밋 메시지 언어를 따른다. 템플릿은 이 스킬 디렉토리의 `references/pr-temp.md`를 Read로 읽어 사용한다.

### 4. 제목과 본문 작성

- **제목**: 70자 이내, 커밋 컨벤션과 같은 형식(`type(scope): 요약`). 커밋이 하나뿐이면 그 메시지를 기준으로 하고, 여러 개면 전체를 아우르는 type을 고른다.
- **본문**: 템플릿의 섹션을 모두 채운다. 해당 사항이 없는 섹션은 지우지 말고 "해당 없음"(KR) / "N/A"(EN)로 둔다. 구조가 일정해야 리뷰어가 읽기 쉽다.
- 테스트 항목은 **실제로 실행한 것만** 체크한다. 실행하지 않은 검증을 완료로 표시하면 리뷰어가 잘못된 안도감을 갖는다. 프로젝트의 테스트/린트 명령은 `AGENTS.md`나 `package.json`에서 찾아 실행해 결과를 반영한다. 실행이 어렵다면 체크하지 않고 이유를 적는다.
- 현재 세션에 PR attribution 지침이 있으면 본문 맨 끝에 그대로 덧붙인다.

### 5. 푸시와 PR 생성

1. upstream이 없거나 로컬이 앞서 있으면 현재 브랜치만 push한다: `git push -u <remote> <현재 브랜치>`. 기본 브랜치로의 push, `--force`는 하지 않는다.
2. 본문은 HEREDOC으로 `--body-file -`에 전달해 줄바꿈과 따옴표가 깨지지 않게 한다.

   ```bash
   gh pr create --base <기본 브랜치> --title "<제목>" --body-file - <<'EOF'
   <본문>
   EOF
   ```

3. 사용자가 draft를 원한다고 말한 경우에만 `--draft`를 붙인다.
4. 실패하면 우회하지 말고 에러를 그대로 보고한다.

### 6. 보고

마지막 메시지에 아래를 담는다. 포크 컨텍스트의 결과는 이 메시지만 사용자에게 전달된다.

- PR URL
- 제목과 base ← head 브랜치
- 선택한 템플릿 언어와 그 근거
- 기본값으로 결정한 사항(push 여부, draft 여부 등)과 미커밋 변경 같은 주의점

## 하지 말아야 할 것

- 커밋, 파일 수정, 기본 브랜치로의 push, force push, PR 머지는 하지 않는다.
- 변경 내용에서 확인되지 않는 사실(성능 개선 수치, 이슈 번호, 실행하지 않은 테스트 결과)을 본문에 쓰지 않는다.
- 변경에 `.env`, 키, 토큰 같은 민감 정보가 보이면 PR을 만들지 않고 파일 위치만 보고한다.
